# 후보 설명 및 LLM-as-a-Judge 입력 감사

## 결론

기존 `description`은 YouTube 롱폼의 메타데이터 설명이 아니다. Vpick 영상 분석
결과에서 후보 시간 구간과 겹치는 여러 장면의 장면명과 설명을 이어 붙인 값이다.
후보 내부의 시각 정보를 제공한다는 점에서는 유효하지만, 여러 장면이 단순 병합되어
후보 밖 내용이나 서로 다른 사건이 섞일 수 있으므로 하나의 숏폼 설명으로 직접
사용하기에는 일관성이 부족했다.

이에 60개 후보 각각에 대해 Vpick 구간 설명과 최종 자막만 읽고, 후보 내부의 중심
사건·행동·반응·결과를 1~2문장으로 다시 작성했다.

## 설명 생성 통제

- 사용 정보: 익명 후보 ID, 길이, Vpick 구간 장면 설명, 최종 자막
- 제외 정보: 제목, YouTube 메타데이터 설명, 채널, Pos/Neg, 조회수, 좋아요,
  성과 백분위, URL, 전후 문맥
- 생성 방식: Codex 직접 작성 및 전수 검수
- 후보 수: 60
- 누락·중복: 0
- 공백 제외 길이: 최소 46자, 최대 64자, 평균 53.73자
- 내용 원칙: 사실 요약만 작성하고 재미·품질·성과 판단 표현은 배제

설명 생성이 끝난 뒤에만 비공개 라벨을 결합해 길이 편향을 확인했다. Pos 30개의
평균은 53.07자, Neg 30개의 평균은 54.40자로 실질적인 길이 차이가 없었다.

## Fable 5 지적 검증

### 맞는 지적

1. 과거 v7 프롬프트에는 출력 차원을 최종 순위 점수로 합치는 식이 명시되지 않았다.
   실행 코드는 체크리스트 평균만 기본 점수로 사용해 프롬프트와 분석 규약이
   분리되어 있었다.
2. v7의 독립 pointwise 평가 지시와 전체 점수 분포 제한은 서로 양립할 수 없다.
3. v7의 불확실 시 중간 점수 부여 문구는 중앙값 쏠림을 유도한다.
4. abstain을 순위·상관·AUC에서 어떻게 처리할지 명시할 필요가 있다.
5. 전체 후보가 공개된 편집 구간이라는 전제는 실서비스의 미게시 후보 평가와
   일치하지 않는다.
6. 근거를 먼저 기록한 뒤 점수를 부여하도록 출력 순서를 바꾸는 것이 적절하다.

### 이미 해결됐거나 사실과 다른 지적

1. 현재 최종 60개 Judge 입력에는 `title` 컬럼이 없다. Pos 10건에만 title이
   있다는 진단은 현재 입력 파일에는 해당하지 않는다.
2. 현재 실행기 `run_shortform_judge_v9.py`는 병렬 실행 여부와 관계없이 후보
   한 개당 모델 호출 한 번을 수행한다.
3. 증거 충분성 점수는 기존 v8/v9 집계식에도 포함되지 않는다. 다만 이를 프롬프트와
   설정 파일에 더 명시적으로 고정할 필요는 있다.
4. v9에는 이미 편집 품질과 콘텐츠 잠재력을 50:50으로 합치는 사전 고정식이 있다.

## v10 반영 사항

- 여러 Vpick 장면을 이어 붙인 설명 대신 후보별 숏폼 설명 사용
- 후보 한 개당 요청 한 번을 명시
- 점수 분포 제한과 중간값 기본 규칙 제거
- 최상위 근거와 차원별 근거를 점수보다 먼저 작성
- 증거 충분성·confidence·failure flag를 순위 점수에서 제외
- abstain 후보는 순위와 성능 지표에서 제외하고 abstain율만 별도 보고
- 편집 품질 4개 차원과 콘텐츠 잠재력 4개 차원을 각각 동일 가중치로 합산
- 두 축을 50:50으로 결합한 `judge_score_100` 사용

## 검증

새 블라인드 입력은 60개 후보와 60개 설명이 일대일 대응한다. v10 설정을 기존
pointwise 실행기에 연결해 dry-run 60개와 mock 3개 후보 2회 반복을 실행했으며,
스키마 검증과 고정 집계 계산이 모두 통과했다. 실제 외부 모델 호출은 수행하지
않았다.
